# STEP 7: Redis 기반 랭킹 서비스 디자인 보고서 (아쉬운 사례)

## 1. 개요
콘서트 예약 시나리오에서 "빠른 매진 랭킹"을 제공하기 위해 Redis를 활용한 랭킹 시스템을 설계 및 구현하였습니다. 
본 보고서는 초기 단계의 구현 내용을 담고 있으며, 의도적으로 단순하고 아쉬운 설계 포인트를 유지하고 있습니다.

## 2. 시스템 디자인

### 자료구조 및 키 설계
- **자료구조**: Redis Sorted Set (ZSET)
  - 스코어 기반으로 자동 정렬되는 특성을 활용하여 랭킹을 구현했습니다.
- **키 설계**: `concert:ranking`
  - 단일 키 하나에 모든 콘서트 정보를 저장합니다.
- **멤버(Member)**: `concertId`
- **스코어(Score)**: 예약 발생 횟수 (단순 카운트)

### 랭킹 정의 및 수집 시점
- **랭킹 정의**: "가장 많은 예약 요청이 발생한 콘서트"를 인기도가 높은 랭킹으로 정의했습니다.
- **수집 시점**: `ReserveSeatInteractor`에서 좌석 선점 및 예약 레코드 생성 직후에 Redis의 `ZINCRBY` 명령을 수행합니다.

## 3. 구현의 한계 및 문제점 (회고)

현 단계의 구현에서는 다음과 같은 문제점들이 식별되었습니다.

### (1) 모호한 랭킹 지표
- "빠른 매진 랭킹"이라고 명명했으나, 실제로는 단순히 '예약 요청 수'를 카운트하고 있습니다. 
- 실제 매진 여부나 매진까지 걸린 시간 등을 고려하지 않아 정확한 의미의 '빠른 매진' 순위를 대변하지 못합니다.

### (2) Redis 키 설계의 확장성 부족
- `concert:ranking`이라는 단일 키만 사용하므로, 콘서트의 회차별, 날짜별, 지역별 랭킹으로 확장하기 어렵습니다.
- Redis의 Key에 대한 TTL(Time To Live) 설정이 없어, 오래된 데이터가 영구적으로 남아 메모리를 점유할 위험이 있습니다.

### (3) 원자성 및 일관성 결여
- DB 예약 처리와 Redis 랭킹 업데이트가 별도의 커넥션/트랜잭션으로 처리됩니다.
- 만약 DB 처리는 성공했으나 Redis 업데이트 중 장애가 발생하거나, 반대로 결제가 취소되어 예약이 무효화되어도 랭킹 점수는 차감되지 않는 등 일관성 문제가 존재합니다.

### (4) 레이어 침범 및 책임 분리 미흡
- `ReserveSeatInteractor` 서비스 레이어에서 직접 `ConcertRankingService`를 호출하고 있습니다. 
- 랭킹 수집은 부가적인 관심사(Cross-cutting concern)임에도 불구하고 메인 로직에 강하게 결합되어 있어 유지보수성을 떨어뜨립니다.

## 4. 테스트 결과
- `ConcertRankingIntegrationTest` 수행 결과, 예약 동작에 따라 Redis의 Sorted Set 스코어가 정상적으로 증가하고 상위 랭킹이 조회됨을 확인하였습니다.
- 하지만 단순 스코어 증가 외에 대량 트래픽 상황에서의 정합성이나 만료 정책에 대한 검증은 포함되지 않았습니다.
