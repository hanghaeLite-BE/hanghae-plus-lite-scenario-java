# STEP 5: Concurrency & Finalize

## 1. 동시성 이슈 식별 및 해결 전략

### A) 좌석 임시 배정 동시성 제어
- **문제 상황**: 동일한 좌석에 대해 여러 사용자가 동시에 예약(RESERVED)을 요청할 경우, 인스턴스 수준의 검증만으로는 중복 예약이 발생할 수 있음.
- **해결 전략**: **조건부 UPDATE (Atomic Update)** 사용.
    - SQL: `UPDATE seats SET status='RESERVED', ... WHERE id=? AND (status='AVAILABLE' OR reserved_until < now)`
    - 별도의 락을 잡지 않고 DB의 원자적 업데이트 기능을 활용하여 성능 최적화 및 동시성 보장.
    - 결과값이 1이면 성공, 0이면 이미 타인이 점유한 것으로 판단.

### B) 잔액 차감 동시성 제어
- **문제 상황**: 한 사용자가 여러 기기에서 동시에 결제를 시도하거나, 충전과 결제가 동시에 일어날 때 갱신 분실(Lost Update) 또는 음수 잔액이 발생할 수 있음.
- **해결 전략**: **비관적 락 (SELECT FOR UPDATE)** 사용.
    - `@Lock(LockModeType.PESSIMISTIC_WRITE)`를 사용하여 Member 엔티티 조회 시점부터 락을 획득.
    - 포인트는 충전/차감 모두 중요 데이터이며, 충돌 가능성이 있는 상황에서 정합성을 확실히 보장하기 위함.

### C) 배정 타임아웃 해제 스케줄러
- **문제 상황**: 예약 후 5분 내 결제되지 않은 좌석들이 시스템에 계속 RESERVED 상태로 남아있어 타인이 예약하지 못하는 상황.
- **해결 전략**: **Spring Scheduler + 조건부 UPDATE** 사용.
    - 1분마다 만료된 (`reserved_until < now`) 좌석을 찾아 `AVAILABLE`로 변경.
    - 스케줄러 자체의 동시성 문제는 DB 수준의 조건부 UPDATE로 방어.

## 2. 테스트 결과

### A) 좌석 중복 예약 테스트 (멀티스레드)
- **방법**: `ExecutorService`(10개 스레드)와 `CountDownLatch`를 사용하여 동일 좌석에 대해 동시에 10건의 예약 요청 발송.
- **결과**: 1건만 성공하고 9건은 실패(또는 예외 발생)함을 검증.

### B) 잔액 이중 차감 테스트 (멀티스레드)
- **방법**: 잔액이 10,000포인트인 유저가 6,000포인트 좌석을 동시에 2회 결제 시도.
- **결과**: 첫 번째 요청만 성공하여 잔액이 4,000원이 되고, 두 번째 요청은 잔액 부족으로 실패함을 검증.

### C) 예약 만료 해제 테스트
- **방법**: `reserved_until`이 과거인 좌석 생성 후 스케줄러 로직 실행.
- **결과**: 좌석 상태가 `AVAILABLE`로 정상 복구됨을 확인.
