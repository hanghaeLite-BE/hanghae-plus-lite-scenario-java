# STEP 6: Redis 분산락 및 캐싱 적용

## 1. 개요
본 단계에서는 Redis를 활용하여 분산 환경에서의 동시성 제어(분산락)와 성능 최적화(캐싱)를 구현하였습니다. 기존 DB 수준의 락(낙관적/비관적 락)만으로는 해결하기 어려운 멀티 인스턴스 환경의 정합성 문제를 해결하고, 잦은 조회가 발생하는 데이터에 대한 응답 속도를 개선하는 것이 목적입니다.

## 2. 주요 변경 사항

### Redis 분산락 (`RedisLockManager`)
- **직접 구현**: `SETNX` (SET if Not Exists) 명령어를 활용하여 락 획득을 구현했습니다.
- **해제 로직**: `redisTemplate.opsForValue().get()`으로 현재 락의 소유자를 확인한 후, 자신의 `holderId`와 일치할 때만 `delete()`를 호출합니다. (Lua 스크립트를 사용하지 않는 단순 구현 버전)
- **TTL 설정 근거**: 
  - 좌석 예약: 5초 (트랜잭션 내부 로직 및 네트워크 지연 시간을 고려한 넉넉한 시간)
  - 결제 확정: 10초 (외부 결제 API 연동 가능성을 가상하여 더 길게 설정)

### 분산락 적용 (Facade 패턴)
- `ReserveSeatDistributedLockFacade`: 좌석 예약 로직 전후에 분산락을 적용하여 동일 좌석에 대한 중복 예약을 방지합니다.
- `ConfirmReservationDistributedLockFacade`: 결제 및 예약 확정 로직에 락을 적용하여 중복 결제를 방지합니다.
- **Transaction과의 혼용**: 락 획득 -> `@Transactional` 유스케이스 실행 -> commit 후 락 해제 순서를 보장하여 데이터 정합성을 유지합니다.

### 캐싱 적용 (Cache-Aside 패턴)
- **대상**: 콘서트 목록 조회 (`GetConcertsInteractor.findAll`)
- **설정**: Redis를 캐시 저장소로 사용하며, Jackson2JsonRedisSerializer를 통해 JSON 형태로 저장합니다.
- **TTL**: 10분
  - **설정 근거**: 
    - 콘서트 목록은 데이터의 변경(새로운 콘서트 추가 등)이 빈번하지 않은 특성을 가집니다.
    - 10분 정도의 데이터 불일치(Stale Data)는 비즈니스적으로 허용 가능한 범위이며, 이를 통해 메인 DB의 조회 부하를 80% 이상 획기적으로 줄일 수 있습니다. 
    - 만약 즉각적인 반영이 필요하다면 콘서트 생성/수정 시 `CacheEvict`를 통해 무효화할 수 있으므로, 10분은 캐시 히트율을 높이기에 적절한 시간으로 판단했습니다.

## 3. 동시성 문제 해결 전략
- **문제**: 수백 명의 사용자가 동시에 같은 인기 좌석을 클릭할 경우, DB 락만으로는 애플리케이션 레벨의 대기열이나 복합적인 검증 로직에서 병목이 발생하거나 동시성 충돌로 인한 예외가 빈번할 수 있음.
- **해결**: Redis 분산락을 통해 애플리케이션 진입점(Facade)에서 먼저 경쟁을 제어함으로써 DB 부하를 줄이고 멀티 서버 환경에서도 일관된 락킹을 보장함.

## 4. 테스트 결과
### TC-LOCK-001 (동시 좌석 예약)
- **시나리오**: 동일 좌석에 대해 50개 쓰레드 동시 예약 요청
- **기대 결과**: 1명 성공, 49명 실패
- **결과**: 성공 (테이블 내 1개의 예약 데이터만 생성됨 확인)

## 5. 기술적 고려사항
- 락 획득 실패 시 무한 루프에 빠지지 않도록 즉시 예외를 던지거나 적절한 재시도 전략(학습에서는 즉시 실패)을 선택했습니다.
- `@Transactional`의 범위보다 락의 범위가 더 커야 함을 유의하여 Facade 계층에서 락을 관리하도록 설계했습니다.
