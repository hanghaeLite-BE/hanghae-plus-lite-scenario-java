# 10주차 필수과제 보고서 (기본 부하 테스트)

## 1. 과제 목적
- 콘서트 예약 서비스에서 트래픽이 몰릴 때 핵심 API가 정상 동작하는지 확인한다.
- 특히 예약/결제 확정 구간에서 동시성 문제가 있는지 확인한다.
- 큰 문제 없이 서비스가 돌아가는지 빠르게 점검하는 것을 목표로 했다.

## 2. 부하 테스트 대상 선정
### 선정 API
- `POST /api/reservations` (좌석 예약)
- `POST /api/reservations/{reservationId}/confirm` (예약 확정/결제)
- `GET /concerts` (콘서트 목록 조회)

### 선정 이유
- 예약/확정은 실제 사용자들이 많이 쓰는 핵심 기능이라서 우선 테스트했다.
- 조회 API는 상대적으로 호출량이 많다고 판단해서 같이 포함했다.

## 3. 테스트 환경
- 애플리케이션: Spring Boot 단일 인스턴스
- DB: MySQL (docker-compose)
- 캐시/락: Redis
- 메시징: Kafka (로컬 구성)
- 부하 도구: k6
- 실행 환경: 로컬 PC

## 4. 테스트 시나리오
### 시나리오 A: 기본 Load Test
- 가상 사용자: 120 VUs
- 지속 시간: 5분
- 요청 비율
  - 예약 50%
  - 확정 30%
  - 조회 20%

### 시나리오 B: Peak Test
- 가상 사용자: 300 VUs
- 지속 시간: 2분
- 요청 비율
  - 예약 60%
  - 확정 30%
  - 조회 10%

## 5. 목표 지표 (사전 설정)
- 평균 응답시간: 500ms 이하
- p95 응답시간: 1,200ms 이하
- 에러율: 3% 이하
- 처리량: 180 req/s 이상

> 참고: 위 목표치는 팀 내부 경험 기반으로 대략 설정했으며, 상세 산정 근거는 별도로 작성하지 않았다.

## 6. 테스트 결과
### 결과 A (120 VUs, 5분)
- 총 요청 수: 54,120
- 평균 응답시간: 412ms
- p95 응답시간: 1,080ms
- 최대 응답시간: 2,430ms
- 에러율: 1.6%
- 처리량: 180.4 req/s

### 결과 B (300 VUs, 2분)
- 총 요청 수: 41,760
- 평균 응답시간: 689ms
- p95 응답시간: 1,980ms
- 최대 응답시간: 4,920ms
- 에러율: 4.8%
- 처리량: 348.0 req/s

## 7. 관찰 내용
- 120 VUs에서는 목표치를 대부분 만족했다.
- 300 VUs 피크 구간에서는 p95와 에러율이 기준을 넘었다.
- 확정 API에서 간헐적으로 지연이 커졌고, DB 락 대기 시간이 증가하는 패턴이 보였다.

## 8. 개선 아이디어
- 예약/확정 쿼리 인덱스 점검
- 확정 트랜잭션 범위 추가 축소 검토
- 피크 대응을 위해 인스턴스 수평 확장 기준 수립
- 부하 테스트 기준값(목표 TPS/응답시간)의 산정 근거 문서화

## 9. 결론
- 기본 부하(120 VUs)에서는 서비스 운영이 가능한 수준으로 보인다.
- 피크(300 VUs)에서는 응답시간과 에러율이 악화되어 추가 개선이 필요하다.
- 다음 단계로 병목 구간 분석 및 재테스트를 진행할 계획이다.
