# 10주차 필수과제 보고서 (기본 부하테스트, 개선본)

## 1. 목적과 검증 범위
- 목적: 콘서트 예약 서비스의 핵심 사용자 여정(조회 -> 예약 -> 확정)이 목표 트래픽에서 안정적으로 동작하는지 검증한다.
- 범위 API
  - `GET /concerts` (목록 조회)
  - `POST /api/reservations` (좌석 예약)
  - `POST /api/reservations/{reservationId}/confirm` (결제 확정)
- 비범위
  - 장시간 내구성(6시간 이상), 인프라 이중화 장애 주입, 네트워크 단절 복구 시나리오

## 2. 목표치 산정 근거
### 2.1 비즈니스 가정
- 이벤트 오픈 10분 동안 진입 사용자: 12,000명
- 사용자 행동 비율
  - 조회 수행률: 100%
  - 조회 후 예약 시도율: 35%
  - 예약 후 확정 시도율: 22%
- 버스트 계수(피크 보정): 1.5

### 2.2 API별 목표 TPS 계산
- 조회 TPS: `(12,000 x 1.00 / 600초) x 1.5 = 30 TPS`
- 예약 TPS: `(12,000 x 0.35 / 600초) x 1.5 = 10.5 TPS`
- 확정 TPS: `(12,000 x 0.22 / 600초) x 1.5 = 6.6 TPS`
- 합계 목표 처리량: 약 `47 TPS`

### 2.3 성능 목표(SLO)
- 성공률: `99.0% 이상` (5xx + 비즈니스 실패 제외)
- 응답시간
  - 조회 API p95: `400ms 이하`
  - 예약/확정 API p95: `900ms 이하`
- 운영 여유율: 목표 TPS 대비 `2배(94 TPS)`까지는 성능 급락 없이 수용

## 3. 테스트 환경
- 애플리케이션: Spring Boot 단일 인스턴스
- DB: MySQL (Docker Compose)
- Redis: 분산 락/캐시
- Kafka: 이벤트 발행/소비 로컬 구성
- 부하 도구: k6
- 실행 환경: 로컬 머신 (CPU 10core, RAM 32GB)

## 4. 테스트 설계
### 4.1 데이터 준비
- 콘서트 1건, 좌석 5,000건
- 테스트 사용자 20,000명, 포인트 사전 충전 완료
- 좌석 중복 예약이 발생하도록 동일 구역 좌석에 요청 집중(동시성 검증 목적)

### 4.2 시나리오
- `Scenario A: Baseline Load`
  - 60초 워밍업 -> 300초 본구간 -> 30초 쿨다운
  - 50 TPS (조회:예약:확정 = 60:25:15)
- `Scenario B: Peak Burst`
  - 30초 80 TPS -> 90초 120 TPS -> 30초 80 TPS
  - 버스트 상황에서 락 경합/DB 대기 검증
- `Scenario C: Stress`
  - 1분마다 +20 TPS 증가, 최대 220 TPS 또는 오류율 10% 도달 시 종료

## 5. 결과 요약
### 5.1 Scenario A (50 TPS)
- 총 요청: 15,180
- 평균 응답시간: 286ms
- p95 응답시간
  - 조회 241ms
  - 예약 611ms
  - 확정 742ms
- 성공률: 99.4%
- 판정: `목표 충족`

### 5.2 Scenario B (80~120 TPS)
- 총 요청: 18,060
- 평균 응답시간: 503ms
- p95 응답시간
  - 조회 389ms
  - 예약 1,021ms
  - 확정 1,384ms
- 성공률: 97.8%
- 판정: `부분 미충족` (예약/확정 p95, 성공률 기준 미달)

### 5.3 Scenario C (Stress, 최대 220 TPS)
- 성능 꺾임 시작: 약 140 TPS
- 170 TPS 이상에서 타임아웃/락 대기 급증
- 200 TPS 구간에서 오류율 10% 초과로 중단
- 판정: 현재 단일 인스턴스 구성의 안정 한계는 `약 130~140 TPS`

## 6. 병목 분석
- 확정 API에서 트랜잭션 구간이 길어질 때 DB 락 대기 동반 증가
- 동일 좌석군에 요청이 몰릴 때 Redis 락 획득 재시도가 증가하며 tail latency 확대
- 조회 API는 상대적으로 안정적이며 병목 기여도가 낮음

## 7. 개선안 및 우선순위
1. 예약/확정 트랜잭션 범위 최소화
- 외부 연동 및 부가 작업을 커밋 이후 비동기 처리로 분리
2. DB 인덱스/쿼리 플랜 점검
- 예약 상태/좌석 상태 조건 조회 인덱스 보강
3. 락 세분화
- 좌석 단위 키 전략 점검 및 락 대기 시간 상한 조정
4. 운영 스케일 기준 수립
- 90 TPS 이상 시 인스턴스 증설하도록 오토스케일 정책 후보 작성

## 8. 결론
- 목표 트래픽(47 TPS) 대비 2배 수준(94 TPS)까지는 운영 가능성이 확인됐다.
- 피크 120 TPS 이상에서 예약/확정 API 지연과 실패율 상승이 확인되어 개선이 필요하다.
- 다음 주차에는 개선안 반영 후 동일 시나리오로 재측정하고, 120 TPS 구간의 성공률 99% 달성을 목표로 한다.
