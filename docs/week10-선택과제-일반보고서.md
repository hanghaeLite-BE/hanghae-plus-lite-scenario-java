# 10주차 선택과제 보고서 (장애 대응 매뉴얼)

## 1. 과제 목적
- 부하 테스트 중 발생 가능한 장애 상황을 정리하고 대응 절차를 만든다.
- 장애 발생 시 빠르게 공유하고 복구할 수 있도록 최소한의 매뉴얼을 만든다.

## 2. 사전 점검 대상
- 예약 API(`POST /api/reservations`) 에러율
- 확정 API(`POST /api/reservations/{reservationId}/confirm`) 응답시간
- DB 커넥션 사용량
- Redis 연결 상태
- Kafka consumer 지연 여부

## 3. 장애 시나리오
### 시나리오 1: 피크 트래픽에서 확정 API 지연
- 징후
  - 평균 응답시간 1초 이상
  - p95 2초 이상
  - 5xx 에러율 5% 내외
- 영향
  - 결제 확정 지연으로 사용자 이탈 가능

### 시나리오 2: DB 락 경합 증가
- 징후
  - DB 락 대기 증가
  - 타임아웃/데드락 로그 증가
- 영향
  - 예약/확정 실패율 증가

### 시나리오 3: 외부 연동(Kafka 소비 지연)
- 징후
  - 이벤트 소비 지연
  - 후속 데이터 반영 지연
- 영향
  - 실시간 집계/전송 지연

## 4. 장애 대응 프로세스
1. 장애 탐지
- 애플리케이션 로그, 에러율, 응답시간 지표 확인
- 임계치 초과 시 장애로 판단

2. 장애 전파
- 팀 슬랙 채널에 장애 발생 공지
- 포함 내용: 시각, 영향 API, 현재 증상, 담당자

3. 1차 조치
- 트래픽 급증 시 인스턴스 스케일 아웃
- DB 락 대기 증가 시 문제 쿼리 확인 후 임시 우회
- Kafka 지연 시 consumer 상태 재기동 검토

4. 복구 및 공유
- 지표 정상화 확인 후 상황 종료 공지
- 장애 영향 범위와 임시 조치 내용 공유

5. 사후 회고
- 원인, 재발 방지 액션, 담당자/기한 정리

## 5. 부하 테스트 기반 참고 수치
- 기준 테스트: 120 VUs 5분
  - 평균 412ms, p95 1,080ms, 에러율 1.6%
- 피크 테스트: 300 VUs 2분
  - 평균 689ms, p95 1,980ms, 에러율 4.8%

> 참고: 임계치 기준은 테스트 결과를 참고해 대략적으로 정했으며, 트래픽 추정 모델 기반의 상세 근거는 부족하다.

## 6. 재발 방지 액션
- 쿼리 튜닝 및 인덱스 재검토
- 락 범위 축소와 트랜잭션 경계 점검
- 에러율/응답시간 Alert 룰 세분화
- 장애 보고서 템플릿 고정화
